## 兔格拼豆 H5：点「编辑」工具条不显示（第三轮）
- 现象：点预览工具条的「编辑」，手绘条 `#et-group` 看不到。
- 根因：`setEditOn(on)` 里量 `state._pvRatio` 的顺序错了——**先量高度、后 `refreshEditUI()` 显形工具条**。量到的比例 ≈ 满屏（没给工具条留位），锁死后 `previewShell` 占掉整屏，工具条被顶到可视区外，又被 `position:sticky; bottom:0` 的底栏盖住，只剩十几像素 → 看起来「没显示」。
- 修法：把 `refreshEditUI()` 提到量高度**之前**（此时仍在普通布局、无 `edit-mode`），量到的 `h` 天然让过工具条那一份；`applyPvLock` 的 `Math.round` 改 `Math.floor`，宁可少 1px 也别因进位把工具条顶出去。
- 通用教训：**凡是「量尺寸 → 锁尺寸」的布局，量之前必须让最终要占位的元素已经处于显示态**，否则量到的是缺项的值。

## 兔格拼豆 H5：展开/收起动画（第四轮）
- 需求：点「编辑」出工具条要有动画（对齐「更多」面板），且两处动画都要**更柔**——「现在太快太线性」。
- **根因（这是重点）**：`max-height` 过渡是「替身动画」，目标值给太大就会**早早露完、后段空转**。参数面板内容实际只有 ~230px，而 `max-height: 48vh`（≈374px）→ 过渡走到 61% 内容就全展开了，剩下 39% 时间什么都不动 = 观感「一下弹出来」。修法：目标高度一律**按内容实际高度给死的值**（JS 读 `scrollHeight` 写进 `style.maxHeight`，CSS 只留 48vh 兜底防矮屏溢出）。
- 动效令牌（写进 `:root`，全项目共用一套）：`--dur-soft: .5s`、`--dur-ease`→`--ease-soft: cubic-bezier(.215,.61,.355,1)`（easeOutCubic）、`--dur-fade: .42s`、`--rise: 5px`。JS 侧对应常量 `SOFT_MS = 500`，两边必须同步改。
- 工具条 `#et-group` 改成和 `.panel-collapse` 同一套折叠：结构上包一层 `.et-group-inner`（内层扛 padding，外层只管折叠），收起态 = `max-height:0` + `border-width:0` + `margin:0` **三者一起过渡**（只动 max-height 会留一条 2px 卡片边线 + 一段空隙）；`[hidden]` 属性弃用，改 `is-open` 类。`box-sizing:border-box` 下 max-height 夹的是边框盒 → JS 目标值要 `内容高 + 2`（上下边框）。
- **必须踩过一次的坑**：起点/终点样式写在同一帧里，浏览器只看得到最终值，**不产生过渡**（表现成瞬移）。要 `add('no-anim')` → 落起点 → `void el.offsetHeight` 强制回流 → `remove('no-anim')` → 改终点。`no-anim` 要对子元素也生效。另外状态没变要 early-return，否则重放动画会闪。内层工具条两排再加 `opacity 0→1` + `translateY(-5px→0)`，第二排 `transition-delay:.06s`（延迟写在 `.is-open` 规则里，收起时自动不生效）。
- **删掉了「预览框像素高度锁定」**（`applyPvLock`/`unlockPvRatio`/`state._pvRatio`、`#screen-edit.edit-mode .preview-shell{flex:none}`）。它只保证「切换瞬间不跳」，代价是工具条没地方长、会被挤出可视区又被 sticky 底栏盖住——上一轮那个「菜单不显示」的 bug 就是它引起的。现在预览保持 `flex:1`，随工具条**平滑让位**，尺寸连续变化交给已有的 `ResizeObserver` + 幂等 `syncViewportResize()`（已实测：各状态下作品中心与容器中心偏差 < 1px）。
- 顺带：固定定位的 toast 会压住底部那一摞（工具条/面板/操作栏），改为弹之前按**展开后的目标高度**（`style.maxHeight`）算 `bottom`；**不能按当前高度算**——工具条刚点开那一帧高度还是 0。footer 加了 `id="footer-bar"` 供测量。

## 兔格拼豆 H5：快手读图失败（第五轮）
- 现象：同一份代码，小红书能读图，快手 webview 弹 `toast('图片读取失败')`。`dist/kuaishou` 与 `dist/xiaohongshu` 的 JS/CSS 逐字节相同（快手只多一段隐藏页内标题的 platform CSS），排除打包差异。
- 根因：`fileInput` 的 `change` 里 **`loadFile(f)` 之后同步 `fileInput.value = ''`**。`loadFile` 走的是异步的 `createObjectURL` → `img.onload`，清空 input 会让相册临时文件在解码前被回收 → `onerror`。对照：同仓库 `crop-grid`（小红书+快手都已上线，同样 `createObjectURL` 读图）把 `value = ''` 放在**整个异步处理结束之后**，所以它能读。已按此改。
- 顺带三处加固：①`loadFile` 加 `FileReader` data: URL 兜底（blob 路失败/12s 超时自动重试一次），②`#file-input` 从 `display:none` 改屏幕外定位（隐藏 file input 在部分 WebKit 里 `<label for>` 激活不可靠），③`accept` 补 `image/heic,image/heif`。
- **通用结论：`<input type="file">` 的 `value = ''` 必须等异步读图结束后再做**，且容器内的读图链路要留一条 data: URL 退路。

## 兔格拼豆 H5：快手保存图纸「提示已保存但相册没有」（第六轮）
- 根因：非小红书容器（快手/抖音）**没有任何存相册原生桥**，`saveOneDataUrl` 落到兜底分支 `a.href = dataUrl(!!) + a.download + a.click()`，然后 **无条件 `Promise.resolve()`** → `done(true)` → 报「已保存到相册」。这条兜底在容器里既不落地、也不报错，等于纯撒谎。
- 额外确认：快手官方文档（小程序/小游戏）只有 `ks.saveImageToPhotosAlbum`，且 `filePath` 必须是本地临时/永久路径、**不支持网络地址也不支持 data: URI**；互动内容世界的接入指南/创作指引通篇没提任何 JSBridge。所以在这个容器里没有可用的编程式存相册。
- 改法：①`saveOneDataUrl` 拆出 `hasSaveBridge()`（仅小红书桥）；②容器内无桥时把图收进 `manualSaves`，导出结束弹 `#save-tip` 浮层——原图铺在可滚动列表里 + 「长按图片保存到相册」提示（长按走系统菜单，是唯一跨容器的通用路径），另给一个可选的「尝试下载」按钮；③`triggerDownload` 一律 `data:→Blob→blob:`（沿用 naming 第七轮的结论，data: URL 挂 `<a download>` 会被当场导航）；④localhost/file 预览仍走下载，不弹浮层。
- 已重出三平台包（各 122 KB）。待真机验证：快手长按图片能否唤起「保存图片」系统菜单。

## 兔格拼豆 H5：快手保存（第七轮，接上轮）
- 真机反馈：浮层里的「尝试下载」按钮**点了没反应** → 说明快手容器里 `<a download>` + `blob:` 也一并被吞（不只是 data:）。**结论：容器内 a[download] 这条兜底基本可以判死**，不要再当可用路径。已删掉该按钮（浮层只留「完成」+ 长按指引），同时把文案补上「没有菜单就截图保存」。
- 新增快手自家桥支持（若有）：`window.ks` + `ks.getFileSystemManager().writeFile({ data: 裸base64, encoding:'base64', filePath: ks.env.USER_DATA_PATH + '/xx.jpg' })` → `ks.saveImageToPhotosAlbum({ filePath })`。快手文档明确 `saveImageToPhotosAlbum` 只吃本地文件路径，**不吃网络地址也不吃 data:**，所以必须先 writeFile。失败/异常一律回落长按浮层，不让用户白点。
- 长按保存的 CSS 坑：目标图**不要写 `user-select: none`**——它可能把 `-webkit-touch-callout` 一起禁掉，表现成「长按图片什么菜单都不弹」。只留 `-webkit-touch-callout: default` + 禁拖拽。
- **真机验证结论（快手，长按可用）**：长按图纸浮层 → 系统菜单「保存图片」→ 相册里确实有。所以快手的保存路径就此定稿＝长按，别再试 a[download] / window.open / 截图以外的东西。
- 已沉淀到 `bead-pattern/README.md` 新增「保存到相册（平台差异）」小节（小红书走桥 / 快手抖音走长按 / 快手小游戏若注入 ks 走 writeFile+saveImageToPhotosAlbum）。
- 快手 Android 无真机可测 → 不为安卓写 UA 分支，改成「自动选路」：有 ks 走 API（两端一致，比长按还顺），没有才长按。另加一个**有依据的**备选：浮层里「系统分享」按钮仅在 `navigator.canShare({files})` 为真时显示（Web Share Level 2；宿主没实现就不出现按钮，杜绝「点了没反应」的假按钮）。
- 用户明确要求：**小红书不能多出保存步骤**。已确认小红书分支没有任何变化（`window.xhs.miniTool.saveImageToPhotosAlbum` 存在就直接 writeTempFile→saveImageToPhotosAlbum，不弹浮层）。只有「小红书客户端老到没有这个 API」才会退到长按浮层（以前是假报已保存）。
